# 第一阶段：函件辅助审查与回函生成

本目录用于开发第一阶段功能，和现有 `deepke_case_extract` 第二阶段安全评估报告审核程序相互独立。第一阶段成熟后，两阶段通过统一字段名对接。

## 本步骤已经建立的文件

- `config/input_schema.json`：统一输入数据结构。
- `config/stage_form_config.json`：不同项目阶段的界面显示和必填提示。
- `config/rule_field_mapping.json`：字段、计算结论、规程条文和审核函数映射。
- `examples/project_input.example.json`：太新路项目的空白示例输入。
- `scripts/validate_input.py`：不依赖第三方库的输入格式校验脚本。
- `scripts/run_calculation.py`：四项规程计算的一键运行入口。
- `rules/`：净距、影响等级、安全评估和保护监测确定性函数。
- `tests/test_rules.py`：规程边界值和端到端测试。
- `scripts/run_letter_extraction.py`：函件PDF抽取和人工字段合并的一键入口。
- `document_processing/`：PDF文本/OCR、函件字段抽取和合并模块。
- `tests/test_document_processing.py`：函件字段与合并策略测试。

## 核心约定

1. 所有距离、深度、长度使用米，面积使用平方米。
2. 不知道的数值填写 `null`，不得用 `0` 代替未知。
3. `其他涉及`使用数组，可同时选择红线、接口、临时结构和协议。
4. 函件抽取值和地图回填值都需要保留来源；地铁结构自动回填后必须人工确认。
5. 正式结论由确定性计算函数产生，大模型只负责函件信息抽取和审核意见文字整理。
6. `chapter_1_functions` 中的条文函数用于记录条文依据；表格数值和公式仍需专门的计算函数。

## 为什么增加了几个输入字段

界面稿中的字段不足以完整执行规程计算，因此增加了以下字段：

- `structure_category`：表3.3.1区分地下装配式、地下现浇、地面和高架结构。
- `original_excavation_depth_m`：附录A中明挖、盖挖结构接近程度所需的 H。
- `outer_diameter_or_width_m`：盾构结构接近程度和上方基坑1.0D控制所需的 D。
- `mined_tunnel_span_m`：矿山法结构接近程度所需的 W。
- `elevated_pile_diameter_m`：高架结构接近程度所需的 P。
- `support_components`：表3.3.1对围护桩、工程桩、锚索等规定不同净距。
- `is_soft_soil`、`confined_water_drawdown`、`disease_severity`：用于3.2.5影响等级提级。

## 四项输出的状态

### 净距控制

- 满足常规净距控制值
- 不满足常规净距控制值，需专题专项论证
- 资料不足

### 影响等级

- 特级、一级、二级、三级、四级
- 资料不足

### 安全评估

- 必须进行
- 建议进行
- 通常不要求
- 资料不足

### 保护监测

- 必须监测
- 必须监测且建议自动化
- 通常不触发
- 资料不足

## 第二步：四项确定性计算

已经实现：

1. 按表3.3.1逐项判断围护桩、地下连续墙、工程桩、锚杆、锚索、土钉和上方基坑净距。
2. 按附录A.0.2计算接近程度。
3. 按附录A.0.3-1计算基坑工程影响分区。
4. 按表3.2.2计算初始影响等级。
5. 按3.2.5检查复杂地质、承压水、特殊区段和大基坑提级因素。
6. 按3.2.6和4.1.2判断安全评估要求。
7. 按7.1.1和7.1.3判断保护监测及自动化监测建议。

### 在 PyCharm 中一键计算

打开并运行 `scripts/run_calculation.py`。默认读取明确标注为非真实项目的 `examples/synthetic_calculation.example.json`，结果写入 `outputs/latest_calculation.json`。

使用新项目时，只需把 `run_calculation.py` 顶部的 `INPUT_FILE` 改为新项目 JSON 路径。

### 在 PyCharm 中运行测试

右键 `tests/test_rules.py`，选择“运行 'Unittests in test_rules.py'”。所有测试通过后，说明当前边界值和四项计算链条未发生回归。

## 真实性处理

- 表3.3.1对软弱土只要求“适当提高并从严控制”，没有统一倍数。程序不会虚构倍数，而是输出“满足表列值，但软弱土地区需从严复核”。
- 3.2.5第3、4款使用“可提高一级”。程序按从严口径给出建议等级，并明确标记需要人工确认。
- 多个3.2.5因素同时出现时只提高一级，不擅自叠加多级。
- `chapter_1_functions` 的条文函数负责保留审核依据，表格数值由本目录中的确定性函数执行。

## 第四步：历史来函—回函数据库与相似回函匹配

第四步已经实现。它不是让模型重新编写审核意见，而是从历史项目中选择最相似的正式回函，并逐字复制该回函“具体意见函复如下”至“特此函复”之间的完整意见正文。

### 4.1 文件扫描与配对规则

默认扫描以下两个历史资料目录：

- `D:\桌面\华设项目\华设`
- `D:\桌面\华设项目\小微工程-报审资料及回函`

程序完成以下处理：

1. 识别 `.doc`、`.docx`、`.pdf` 格式的来函和回函。
2. 根据项目根目录、出让/规划/设计/施工阶段和标题相似度配对来函与回函。
3. 将同一回函的可编辑 Word 和盖章 PDF 归并为一个历史案例。
4. 正文提取优先使用 `.docx`，其次使用 `.doc`，最后使用 PDF。旧版 Word 无法打开而同组存在盖章 PDF 时，自动回退到 PDF OCR。
5. `.doc` 通过本机 Microsoft Word 读取，因此建库时请勿强制结束 Word 进程。
6. 扫描型历史回函自动使用本地 OCR，文件不会上传网络。
7. 历史来函有文字层时直接读取；纯扫描历史来函不重复 OCR，而由回函正文、文件名和路径补充匹配文字。新项目来函仍按第三步执行 300 DPI 精细 OCR。

数据库同时保留 `primary_reply_file`、`editable_reply_file`、`official_reply_file` 和 `reply_files`，不会因去重而丢失正式文件路径。

### 4.2 审核意见提取边界

程序优先识别“具体意见函复如下”“意见如下”“注意如下事项”等真实回函用语，从该位置开始提取，到“特此函复”“此复”之前结束。顶层 `1.`、`2.`、`3.` 被拆分为 `advice_items`，原始完整正文同时保存在 `advice_text`。

`advice_text` 是历史回函原文，不进行摘要、润色或生成。匹配输出中的 `advice_is_verbatim: true` 表示采用了逐字复制方式。

### 4.3 在 PyCharm 中建立数据库

1. 打开 `scripts/build_reply_database.py`。
2. 检查文件顶部 `HISTORY_ROOTS`。新增历史资料根目录时，在该列表增加一行。
3. 右键文件空白处，选择“运行 'build_reply_database'”。
4. 运行窗口会显示 `[当前数量/总数量] 文件名`。首次 OCR 建库可能需要数分钟。
5. 显示“历史回函数据库建立完成”后检查三个输出文件。

输出文件：

- `data/history_replies.sqlite3`：程序使用的 SQLite 数据库。
- `outputs/history_replies_index.json`：人可以直接查看的完整历史案例索引。
- `outputs/history_database_build_report.json`：扫描数量、去重数量和未识别意见警告。

维护历史库时，先在历史资料目录中添加、替换或删除文件，再重新运行 `build_reply_database.py`。脚本会重建索引，已删除的文件不会残留在数据库中。

### 4.4 在 PyCharm 中匹配一个新项目

1. 先完成第三步，得到新项目的 `04_merged_input.json` 和 `函件全文.txt`。
2. 打开 `scripts/match_similar_reply.py`。
3. 将顶部 `INPUT_FILE` 改为新项目的 `04_merged_input.json`。
4. 将顶部 `LETTER_TEXT_FILE` 改为新项目的 `函件全文.txt`。
5. 右键运行 `match_similar_reply.py`。

输出文件：

- `outputs/latest_reply_match.json`：完整匹配结果、前三名候选、各维度得分和历史文件来源。
- `outputs/latest_matched_advice.txt`：最高分达到阈值时，逐字复制的历史审核意见。

### 4.5 相似度如何计算

当前使用可解释的混合相似度，不依赖联网模型。计算维度包括：

- 项目名称：18%
- 项目阶段：17%
- 项目类型：15%
- 相对关系：10%
- 地铁结构形式：10%
- 地铁线路：8%
- 基坑深度：6%
- 水平净距：5%
- 竖向净距：3%
- 来函与项目文字语义：8%

历史资料缺少某项数值时，该项不按零分处理，而是从本次有效维度中排除后重新归一化。文字语义使用中文字符二元组和三元组余弦相似度。结果中的 `component_scores` 会显示每一项得分；`null` 表示历史资料中没有足够数据，未参与本次计算。

默认自动采用阈值为 `0.45`。低于阈值时，`match_status` 为 `manual_review_required`，程序只列出候选项，不生成 `latest_matched_advice.txt`。这能避免在历史资料明显不相似时强行复制意见。

### 4.6 数据质量检查

建库报告中的 `warnings` 需要人工查看，常见情况包括：

- 回函正文中没有识别到“意见如下”一类起始语句。
- 旧版 `.doc` 无法由 Microsoft Word 打开。
- 盖章 PDF 清晰度过低，OCR 未得到有效正文。

可读索引中的 `pair_score` 是来函与回函的配对可信度，不是新案例匹配相似度；新案例的相似度在 `latest_reply_match.json` 的 `similarity_score` 中查看。

## 第三步：函件PDF抽取与人工字段合并

### 支持的PDF

- 文本型PDF：优先使用文字层直接提取。
- 扫描型PDF：自动渲染页面并使用本地RapidOCR识别，文件不会上传到网络。
- 混合型PDF：逐页选择直接提取或OCR。

### 当前抽取字段

- 函件标题
- 项目名称
- 报审单位
- 收函单位
- 项目阶段
- 项目位置
- 建设规模或主要建设内容
- 联系人及联系电话
- 函件日期
- 管径、长度、埋深、规模等测量信息

每个字段同时保存 `confidence`、`source_page`、`source_text`、`extraction_method` 和 `status`。

### 合并原则

1. 人工已填写值优先，抽取值不覆盖人工值。
2. 人工值与抽取值不同时写入冲突清单。
3. 人工字段为空时，仅自动采用置信度不低于0.75且状态为 `extracted` 的值。
4. 红章遮挡的落款单位、日期等低置信度字段进入人工复核清单。

### 在PyCharm中运行

打开并运行 `scripts/run_letter_extraction.py`。更换函件时修改文件顶部的 `PDF_FILE` 和 `MANUAL_INPUT_FILE`。

输出目录包含：

- `01_pdf_text.json`：逐页文字、OCR置信度和坐标。
- `02_extracted_fields.json`：结构化字段和原文证据。
- `03_merge_report.json`：自动填入、冲突及待复核字段。
- `04_merged_input.json`：可供后续规程计算使用的统一输入。
- `函件全文.txt`：便于人工查看的全文。

### 安装依赖

在PyCharm的“Python解释器”页面安装本目录 `requirements.txt` 中的依赖。扫描函件必须安装 `rapidocr_onnxruntime`。

## 在 PyCharm 中检查输入文件

直接打开并运行 `scripts/validate_input.py`，默认检查示例文件。显示 `VALIDATION OK` 表示字段名称、类型、枚举和范围符合统一 Schema。

## 第五步：生成审核意见和回函辅助草稿

第五步将第二步的四项确定性计算与第四步的历史回函匹配结果合并。规程结论和历史经验严格分开：

1. 退让距离、影响等级、安全评估和保护监测只能由 `rules/` 中的确定性函数计算。
2. 每项结论保存实际调用的函数、依据条文、输入值、计算步骤和缺失字段。
3. 历史回函只截取“注意如下事项”之后的子项，不复制历史项目的位置、净距、规模等事实。
4. 历史注意事项逐字复制，并保存来源项目、来源文件和相似度。
5. 任何关键字段缺失时，总体状态为 `blocked_by_missing_data`，不得强行生成正式结论。
6. 所有输出均为辅助草稿，`formal_issuance_allowed` 固定为 `false`，必须经专业人员复核和审批。

### 在 PyCharm 中运行第五步

1. 先完成第三步，得到新项目的 `04_merged_input.json` 和 `函件全文.txt`。
2. 确认第四步数据库 `data/history_replies.sqlite3` 已建立。
3. 打开 `scripts/generate_review_package.py`。
4. 修改文件顶部的 `INPUT_FILE`、`LETTER_TEXT_FILE` 和 `OUTPUT_NAME`。
5. 右键文件，选择“运行 'generate_review_package'”。

默认输出到 `outputs/review_packages/<OUTPUT_NAME>/`：

- `01_calculation.json`：四项规程计算及调用函数。
- `02_history_match.json`：相似历史回函候选及各维度得分。
- `03_review_package.json`：完整、可追溯的审核数据包。
- `审核意见.md`：供审核人员查看的技术审核意见。
- `回函草稿.md`：包含规程结论、资料补充要求和历史注意事项的辅助草稿。

### 总体状态

- `blocked_by_missing_data`：缺少关键参数，先补充资料并重新运行。
- `requires_special_study`：净距不满足常规控制值，需要专题专项论证。
- `ready_for_human_review`：确定性计算已完成，可以进入人工复核，但仍不得直接正式出具。

### 为什么不直接复制整份历史回函

历史回函第一条通常描述旧项目的位置、结构关系和具体净距。这些内容不属于新项目事实，直接复制会造成严重错误。因此第五步只复制可精确定位的“注意事项”子项；新项目概况和四项结论全部来自本次输入与规程计算。

## 第六步：一键流水线和本地桌面界面

第六步将前五步串成一次运行：

1. 读取函件 PDF，自动判断文字层或 OCR。
2. 抽取函件字段，与人工填写参数合并。
3. 按 `input_schema.json` 校验统一输入。
4. 计算退让距离、影响等级、安全评估和保护监测。
5. 从历史数据库匹配最相似回函并截取注意事项。
6. 生成完整审核包、审核意见和回函辅助草稿。

### 方式一：运行桌面界面

在 PyCharm 项目窗口中找到并运行根目录下的 `stage1_reply_system/app.py`。

界面包含四个页签：

- `项目与函件`：选择函件，填写阶段、相对关系和位置。案例编号自动生成，项目名称和报审单位从函件提取，不需要手工填写。
- `地铁结构`：填写结构形式、相应结构尺寸、状态以及线路和区间。
- `基坑与地质`：选择支护构件、保护区状态、地质条件和辅助说明。
- `审核结果`：查看四项结论、缺失字段、历史匹配项目和结果目录。

项目阶段改变时，阶段参数会自动切换：

- 出让：用地性质、水平距离。
- 规划：基坑深度、长度、宽度、面积、水平距离、竖向距离。
- 设计/施工：基坑深度、长度、面积、水平距离、竖向距离、降水方式、专家意见文件、方案文件。

界面中的字段按用途分成三类：

- `计算必填`：直接进入退让距离、影响等级、安全评估和保护监测计算。缺失时，相关结论会显示资料不足或需要补充。
- `条件判断`：用于调整阈值、提高影响等级或触发人工复核。不能确定时应选择“未知”，不要猜填“是”或“否”。
- `辅助信息`：用于项目定位、回函展示、历史案例匹配和结果追溯，不直接决定四项计算结论。

“项目位置”“地图位置名称”和经纬度位于“辅助信息（可选）”区域，均不强制填写。使用地图匹配并自动回填地铁区段资料时再填写或拾取经纬度；完全手工填写地铁结构资料时可以留空。

地铁结构尺寸会根据结构形式动态切换，一次只需填写一个：

- 明挖：原开挖深度 `H`。
- 暗挖（矿山法）：毛洞跨度 `W`。
- 盾构：外径或结构宽度 `D`。
- 高架：单桩桩径 `P`。

切换结构形式时，程序会清空上一种结构形式的无关尺寸，防止旧数值误入审核。

点击“开始审核”后程序在后台执行，界面不会因 OCR 失去响应。完成后点击“打开结果目录”即可查看全部文件。

`项目与函件`、`地铁结构`和`基坑与地质`三个输入页均带有右侧滚动条。页面内容超出窗口时，可以拖动滚动条，也可以将鼠标放在当前输入页的任意输入框或空白处，使用鼠标滚轮上下移动。

项目名称若能从函件标题可靠识别，会自动写入回函标题；报审单位因印章遮挡等原因不能可靠识别时，回函中显示“收函单位待补充”，由办文人员复核填写。程序不会猜测单位名称。

### 方式二：在 PyCharm 中运行一键脚本

打开 `scripts/run_stage1_one_click.py`，修改顶部：

- `PDF_FILE`：函件 PDF。
- `MANUAL_INPUT_FILE`：人工参数 JSON。
- `RUN_NAME`：本次输出名称。

随后直接运行该文件。此方式适合已有标准 JSON 的项目。

### 一键输出目录

每次运行在 `outputs/one_click_runs/` 下新建带时间的独立目录，避免覆盖以前结果。目录包含：

- `00_manual_input.json`：本次人工输入。
- `01_pdf_text.json`：PDF/OCR结果。
- `02_extracted_fields.json`：函件字段。
- `03_merge_report.json`：自动填入、冲突和待复核项。
- `04_merged_input.json`：最终统一输入。
- `05_calculation.json`：四项规程计算。
- `06_history_match.json`：历史回函匹配。
- `07_review_package.json`：完整审核数据包。
- `审核意见.md`、`回函草稿.md`、`函件全文.txt`。
- `run_summary.json`：供界面和后续系统读取的摘要。

### 地图数据说明

第六步界面已保留项目位置、地图位置名称、经度和纬度字段。第七步在此基础上建立“区段—坐标—结构形式—结构状态—埋深”基础数据库，并实现经过用户确认的地图回填。

## 第七步：地图拾取、区段数据库和地铁结构信息回填

第七步已经建立轨道区段基础数据库，并把地图拾取入口接入第一阶段桌面程序。数据库初始为空，不会为现有案例猜测坐标。只有经过核实并由用户录入的区段，才会参与自动匹配。

### 7.1 第一次使用前安装地图依赖

在 PyCharm 中文界面中依次打开：

1. `文件` -> `设置` -> `项目：stage1_reply_system` -> `Python 解释器`。
2. 点击解释器页面中的“安装”或“+”。
3. 搜索并安装 `tkintermapview`，版本选择 `1.30` 或更高的 1.x 版本。

也可以在 PyCharm 的 Python 解释器页面选择本项目的 [requirements.txt](requirements.txt)，安装其中全部依赖。

地图默认使用 OpenStreetMap 在线瓦片。首次浏览某一区域时需要联网；无法联网时仍可手工填写经纬度和地铁结构资料，不影响规则审核的其他部分。

### 7.2 建立轨道区段基础数据库

1. 在 PyCharm 中直接运行 [app.py](app.py)。
2. 打开“项目与函件”页面。
3. 点击经纬度下方的 `区段数据库`。
4. 填写线路、区段名称、结构形式、结构类别、结构状态、埋深、经纬度和资料来源。
5. 点击 `保存`。

必须核实后再录入的字段包括：

- `线路`：例如 1号线。
- `区段名称`：例如某站至某站区间。
- `结构形式`：明挖、暗挖（矿山法）、盾构或高架。
- `结构类别`：由结构形式带出，必要时人工核对。
- `结构状态`：较好或较差，应有巡检或正式资料依据。
- `结构埋深`：单位为米。
- `经度、纬度`：WGS84 十进制度坐标。
- `来源项目、来源文件`：用于说明这些数据从哪里取得。

数据库文件保存在 `data/metro_segments.sqlite3`。界面中的“停用选中记录”是软删除：该记录不再参与新匹配，但不会破坏既往审核结果中的来源编号。

### 7.3 批量导入区段资料

批量录入时使用 [metro_segments_import_template.csv](data/metro_segments_import_template.csv)。不要修改表头，每一行填写一个已经核实的区段参考点，再在“区段数据库”窗口点击 `导入 CSV`。

必需列为：

```text
line_name,section_name,structure_method,structure_category,structure_condition,buried_depth_m,longitude,latitude
```

可选列为：

```text
source_project,source_file,notes
```

CSV 使用 UTF-8 编码。程序会分别报告成功条数和失败条数，不会静默忽略错误坐标、空字段或重复数据。

### 7.4 在地图上拾取项目位置

1. 先在“地铁结构”页面填写已知的地铁线路。线路可以为空，但填写后候选排序更准确。
2. 返回“项目与函件”页面，点击 `地图拾取`。
3. 在地图上单击项目位置，地图会显示“项目位置”标记。
4. 右侧列出 2 公里内的候选区段，并显示实际距离和匹配分。
5. 选中候选区段，核对结构形式、状态、埋深和来源项目。
6. 根据实际情况选择 `仅采用坐标` 或 `采用坐标和选中区段`。
7. 采用区段前，程序会再次弹窗显示区段和距离。确认后才回填地铁结构信息。

候选排序规则是：地理距离占 85%，填写的线路是否一致占 15%。程序使用经纬度球面距离，不会把项目地址文字相似度当作空间距离。

### 7.5 回填字段和来源追溯

确认采用候选区段后，程序回填以下字段：

- 地铁线路 `metro_line_name`
- 地铁区间 `metro_section_name`
- 结构形式 `structure_method`
- 结构类别 `structure_category`
- 结构状态 `structure_condition`
- 结构埋深 `buried_depth_m`

同时在审核输入 JSON 的 `metro_structure.autofill_source` 中记录：

```json
{
  "source_type": "segment_database",
  "source_id": "区段数据库编号",
  "source_name": "线路 / 区段",
  "distance_m": 该区段距项目拾取点的距离,
  "confidence": 匹配分,
  "confirmed_by_user": true
}
```

如果回填后人工修改了任一地铁结构字段，程序不会继续冒用原区段来源，而会按人工填写数据处理。

### 7.6 完整的一键审核操作

1. 运行 [app.py](app.py)。
2. 选择函件 PDF，填写项目阶段、相对关系和阶段参数。
3. 通过地图拾取项目位置并确认候选区段，或完全手工填写地铁结构信息。
4. 填写基坑、地质和保护区信息。
5. 点击 `开始审核`。
6. 在“审核结果”页查看退让距离、影响等级、安全评估、保护监测、历史回函匹配和缺失资料。
7. 点击 `打开结果目录`查看完整 JSON、审核意见和回函草稿。

区段数据库只负责提供经过确认的基础结构信息。退让距离、影响等级、安全评估和保护监测仍由规则模块独立计算，地图匹配分不等于规则审核结论，也不会替代人工复核。

## 第八步：历史来函与回函数据库管理

第八步把原来只能通过脚本建立的历史回函数据库接入桌面主界面。可以持续加入新的项目资料、查看来函与回函是否正确配对、停用不可靠案例，并查看新项目为什么匹配到某份历史回函。

### 8.1 打开历史回函数据库

1. 在 PyCharm 中直接运行 [app.py](app.py)。
2. 点击主窗口底部的 `回函数据库`。
3. 窗口顶部会显示总案例数、启用数、停用数、可匹配数和待复核数。

列表中的状态含义：

- `启用`：该案例可以参与新项目匹配。
- `停用`：保留历史数据和编号，但不再参与匹配。
- `可匹配`：已经找到回函建议正文，来函回函配对也没有明显质量问题。
- `待复核`：存在未配对来函、未提取到建议、配对分偏低或来函文字读取失败等问题。

“待复核”不会自动等同于错误案例。核对原始文件后，可以保留启用，也可以点击 `停用选中案例`将其排除。

### 8.2 增量加入新的来函和回函

1. 在“历史来函与回函数据库”窗口点击 `选择资料文件夹并增量更新`。
2. 选择包含一个或多个项目文件夹的上级目录。
3. 程序递归识别来函、可编辑回函和盖章回函，并按项目目录、阶段和标题进行配对。
4. 等待界面提示更新完成。
5. 核对成功处理数量、数据库总数和警告数量。

增量更新不会清空原数据库。相同回函根据文件路径指纹更新，并保留原案例编号和人工设置的启用/停用状态；新的回函生成新的案例编号。

每次更新报告保存在：

```text
outputs/history_database_updates/日期时间/history_database_update_report.json
```

报告中的 `warnings` 必须人工查看，常见情况包括未识别审核意见、可编辑回函读取失败后改用盖章 PDF，以及扫描文件无法读取。

### 8.3 查看和停用案例

1. 在列表中单击一个案例。
2. 下方会显示质量问题、结构形式、地铁线路、来函路径、回函路径和审核意见原文预览。
3. 点击 `打开回函原文`可以直接打开作为数据库来源的回函。
4. 确认案例不适合匹配时，点击 `停用选中案例`。
5. 后续需要恢复时，选择该案例并点击 `启用选中案例`。

这里采用软停用而不是物理删除，目的是让以前生成的审核结果仍能根据 `history_case_id`追溯到当时使用的历史案例。

### 8.4 新项目匹配结果怎么看

完成一键审核后，“审核结果”页面会显示：

- 历史匹配项目名称
- 总相似度
- 历史案例编号
- 历史案例质量和质量提示
- 实际采用的回函文件路径
- 各个匹配维度的单项得分

分项得分包括项目名称、项目阶段、项目类型、相对关系、结构形式、地铁线路、基坑深度、水平净距、竖向净距和函件语义。分数范围为 0 至 1，越接近 1 表示越相似；`无数据`表示新项目或历史案例缺少该字段，该项不会强行按 0 分计算。

总相似度不是十项简单平均，而是对当前双方都有数据的项目按权重重新归一化。完整计算明细保存在每次审核目录的：

```text
06_history_match.json
```

其中：

- `selected_match`：达到自动采用阈值的历史案例。
- `candidates`：相似度最高的候选案例列表。
- `component_scores`：每个维度的分项得分。
- `primary_reply_file`：实际复制审核意见的回函来源。
- `advice_text`：从历史回函提取的原文，程序不进行改写。

如果最高总相似度低于阈值，`selected_match`为空，程序不会为了生成回函而强行复制一个不相似案例的注意事项。

## 第九步：自动生成 Word 回函草稿和内部审核记录

第九步将原有 Markdown 辅助稿转换为可直接用 Microsoft Word 打开和修改的文件。每次一键审核会同时生成两份用途不同的 Word 文档。

### 9.1 两份 Word 文件的区别

`回函辅助草稿.docx`供办文人员继续修改，包含：

- 项目名称和收函单位
- 四项规程计算结论及条文编号
- 需要补充的资料
- 相似历史回函中的实施注意事项原文
- 文号、落款和日期待填写提示
- “不得直接作为正式复函出具”的内部提示

`内部自动审核记录.docx`供内部复核和追溯，包含：

- 项目基本信息和总体审核状态
- 每项判断的结论、审核意见、依据条文、审核函数和计算过程
- 缺失字段的中文名称和 JSON 字段名
- 匹配的历史案例编号、质量状态、相似度和来源回函路径
- 十项相似度分项得分
- 历史回函注意事项原文
- 复核人、复核结论、修改说明和复核日期填写区

程序将审核函数和匹配分数放在内部记录中，不会混入拟发回函正文。

### 9.2 在 PyCharm 中生成 Word

1. 直接运行 [app.py](app.py)。
2. 按前面步骤填写项目、地铁结构、基坑和地质信息。
3. 点击 `开始审核`。
4. 审核完成后，可以点击 `打开回函 Word`直接打开回函辅助草稿。
5. 点击 `打开审核记录`直接打开内部自动审核记录。
6. 点击 `打开结果目录`可以查看同一次审核生成的全部 JSON、Markdown 和 Word 文件。

无需为 Word 单独配置运行参数。Word 文件与 `run_summary.json`位于同一个日期时间结果文件夹中。

### 9.3 内容真实性边界

- 历史实施注意事项按照回函数据库中的截取原文写入，不自动改写。
- 规程结论来自确定性规则函数，不由语言模型自由生成。
- 没有数据时明确写“资料不足”或“待填写”，不会猜测数值。
- 不自动生成正式文号、单位落款、签发人和签发日期。
- 两份 Word 均为辅助文件，必须经过专业人员复核和审批。

### 9.4 每次一键审核的主要交付文件

```text
回函辅助草稿.docx
内部自动审核记录.docx
回函草稿.md
审核意见.md
05_calculation.json
06_history_match.json
07_review_package.json
run_summary.json
```

Word 用于阅读、修改和内部流转，JSON 用于追溯每个结论的输入、规则函数和历史来源。两者来自同一个审核包，不会分别计算出互相矛盾的结果。
